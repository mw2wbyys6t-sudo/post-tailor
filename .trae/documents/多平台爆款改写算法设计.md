# ContentPort 多平台「爆款」改写算法 —— 设计与实现计划

## Context（为什么做这件事）

现状的改写是**模板拼装**：`js/rewrite.js` 用各平台硬编码的标题/开头/结尾字符串，正文只是把原文 `plain(body)` 截前几行；`js/api.js` 的 AI 版也只是把平台画像 JSON 一次性丢给模型，评分靠 `radar` 均值 + 随机数。结果看起来"变了"，但没有真正按平台重构内容，也无法量化好坏，更谈不上"发到不同平台都能成爆款"。

用户目标：**同一篇文章 → 每个平台都产出真正平台原生的改写稿，最大化成为爆款的可能性**。本计划交付：混合流水线算法 + 分发工作台接入 + 零依赖评测集。

诚实边界（必须写进 UI 与文档）：没有任何算法能"保证爆款"。本方案优化的是**可测量的爆款前置条件**（钩子强度、平台结构合规、信息保留、原创度、可读性），并用真实发布回拉的阅读/点赞数据做后续校准，n<30 不结论。

## 一、算法总览

```
文章(Markdown)
  │
  ├─ analysis.js  内容结构解析：章节/关键句/数字证据/代码块/表格/术语/信息密度/内容类型
  │
  ├─ planner.js   平台策略规划：内容类型 × 平台 → 钩子原型、结构模板、标题公式、字数预算、章节取舍
  │
  ├─ pipeline.js  执行编排
  │     ├─ 有 AI：计划(JSON) → 成稿(JSON) → 本地质检 → 按问题单修复一次 → 复检取更优
  │     └─ 无 AI：writer.js 抽取式确定性成稿（复用同一份 plan，不注水、不编造）
  │
  └─ quality.js   本地质检：7 维加权总分 + 硬门槛 + 可追溯问题单
```

所有引擎文件采用 UMD 写法：浏览器挂 `window.CP.engine.*`，Node 下 `module.exports`，**零依赖**，可被 `eval/run.js` 直接 require。

## 二、模块拆分（新增 `js/engine/`）

| 文件 | 职责 | 关键输出 |
| --- | --- | --- |
| `analysis.js` | 轻量 Markdown 解析（不引第三方库）：`##` 章节、段落、列表、代码块、表格、引用；句子切分；TF-IDF 关键词；数字/百分比/单位证据；结论词句；内容类型判定（教程/经验/观点/测评/科普/案例，信号加权 + `category` 兜底） | `{sections, sentences, keyPoints, numbers, codeBlocks, tables, terms, density, contentType, thesis}` |
| `strategies.js` | 平台策略画像：继承 `mock.PLATFORMS` 的受众字段，补强标题公式库、钩子库、结构模板、长度预算、排版规则、CTA、标签策略、平台禁忌、质检权重；`getPlatform(pid)` / `getMatrix(type, pid)` | 结构化策略配置 |
| `planner.js` | 选钩子/结构/标题公式/字数预算；章节映射 `keep / merge / split / drop`；生成 `mustKeep[]`、`risks[]`、给 AI 的 `brief` | `plan` 对象 |
| `writer.js` | 无 AI 抽取式成稿：按 plan 取原句、句级压缩合并、平台排版；不新增事实，素材不足时显式标注 | `{title, body}` |
| `quality.js` | 本地质检与打分（公式见下），输出问题单 | `{total, dims:{C,S,L,T,O,R,M}, metrics, issues[]}` |
| `pipeline.js` | 编排 + 并发控制（每平台最多 3 次 AI 调用、并发 2、单次 90s 超时）+ JSON 校验/修复重试 + AI 失败降级 writer | 兼容旧字段的改写结果 |

## 三、平台策略：把"爆款"落成可编码规则

**钩子原型 8 种**：结论先行 / 结果前置 / 场景痛点 / 反常识 / 数字清单 / 对比冲突 / 身份代入 / 时间线。

**标题公式库（带平台白名单与字数区间）**
- `R1 {关键词}：{数字}个{结果}`
- `R2 我{时间}做完{痛点}，总结{数字}条`
- `R3 {年份}年，{关键词}还值得做吗？`
- `R4 别再{错误做法}，{正确做法}只要{数字}步`
- `R5 {关键词}实测：{A} vs {B}`
- `R6 关于{关键词}，{人群}该知道的{数字}件事`

**内容类型 × 平台 选择矩阵（节选）**

| 类型 | CSDN | 微信公众号 | 小红书 | 知乎 |
| --- | --- | --- | --- | --- |
| 教程 | 结论先行；结论→背景→步骤→代码→踩坑→数据 | 场景痛点；故事→方法→清单→金句 | 身份代入；结果→3-5 步→避坑→互动 | 反常识；结论→为什么→分点→边界→来源 |
| 经验 | 结果前置 | 故事冲突 | 结果晒单+清单 | 结论+复盘 |
| 观点 | 争议结论 | 现象切入 | 立场短句 | 先结论后论证 |
| 测评 | 结论+维度表 | 选择焦虑 | 红黑榜 | 结论+方法+局限 |
| 科普 | 一句话定义 | 生活比喻 | 3 个冷知识 | 定义+误区 |

**长度预算**：csdn 1200-3000；wechat 1800-4000；xhs 600-1200（且 `max(600, 原文×0.55)`）；zhihu 2500-6000。上限统一 `min(平台上限, 原文×1.8)`，防止注水。

**平台禁忌（P0 硬扣分）**：微信外链/诱导关注分享/极限词；小红书导流词（微信、私信、二维码、链接）与绝对化用语；CSDN 标题党、正文无代码/命令类文章缺实操；知乎营销腔、无来源数据。

**标签策略**：`analysis.keywords ∩ platform.trending` 取 2-4 个；小红书额外 3-5 个 `#` 话题（宽泛 + 垂直搭配）。

## 四、质检评分（quality.js）

```
total = 0.25·C + 0.20·S + 0.10·L + 0.10·T + 0.15·O + 0.10·R + 0.10·M
```

- **C 信息保留** = 0.5×关键点召回 + 0.3×数字召回 + 0.2×章节主题召回
- **S 结构合规** = 钩子 20 + 必备章节 40 + 章节数 15 + CTA 15 + 排版 10
- **L 长度合规**：区间内 100；±15% 为 80；其余按偏离线性扣
- **T 标题** = 字数 35 + 关键词/公式匹配 30 + 具体性（数字/结果）20 + 无标题党 15
- **O 原创度** = `100 − 200×max(0, copyRun − target)`，`copyRun` = 成稿 8-gram 命中原文比例；target：csdn/zhihu 0.55、wechat 0.45、xhs 0.35
- **R 可读性** = 句长 12-38 字 40 + 长句占比 20 + 段落/清单节奏 30 + 术语密度 10
- **M 合规** = 100 − P0×100 − P1×30 − P2×10

硬门槛：出现 P0 或数字召回 < 0.8 → 总分封顶 69。
输出每条 `issue` 含 `{code, level, where, msg, fix}`，可追溯到具体章节/原句。

## 五、LLM 分阶段流水线

- **A 计划**：输入分析结果 + 平台策略 + 用户画像，只输出 JSON（angle/hookId/structureId/titleFormulaId/sections/tags），ID 白名单校验。
- **B 成稿**：只输出 `{title, body, usedFacts[]}`；校验数字必须来自原文数字集合、长度区间、禁忌词。
- **C 质检**：本地 quality.js。
- **D 修复**：`total < 85` 或存在 P1 时，带问题单与当前稿再改一次；复检提升 ≥3 且无新 P0 才采纳。
- JSON 解析复用 `api.js` 的 `parseJsonLoose`（扩展数组容错）；失败以温度 0.2 重试一次，再失败落 `writer.js`，绝不把坏 JSON 入库。

## 六、评测集与 CLI（零依赖）

- `eval/cases/*.json` 共 10 篇：现有教程/经验/案例/测评/科普，另加 450 字观点、6000 字含代码表格教程、纯清单、术语混排、120 字超短。
- `eval/run.js`：`global.window = global` → require mock/rewrite 跑旧基线；参数 `--engine=old|new|both`、`--platforms=`、`--ai`、`--json`、`--fail-under=85`。
- 输出：文章 × 平台 的 total / C-S-L-T-O-R-M / 字数 / issue 数，各平台均值与相对旧引擎增益。
- 判定阈值：离线均值 ≥85；每个平台相对旧引擎 ≥+10；compliance ≥95、coverage ≥80、P0=0、长度合规 100%；AI 相对离线 +5 且 coverage 不降。
- `eval/baseline.json` 记录旧引擎基线，回归下降 >2 退出码 1（可接 CI）。
- **真实校准**：发布记录追加 `algorithm:{engineVersion, dims, contentType, hookId, structureId}`；`eval/calibrate.js` 读导出的 history，按平台算质检分与 `log(views+1)`、点赞率的 Spearman；n≥30 才报告，权重调整限 ±10%，不自动上线。

## 七、页面接入（最小改动）

- `js/api.js`：`rewriteArticle` 每平台改调 `CP.engine.pipeline.run`，异常降级旧 `fallback()`；返回仍保证 `{platformId, platformName, platformColor, title, body, changes, score, keywords, fitted}`，新增 `quality / algorithm / engine`；移除 a1 硬编码 92/90/87/91。
- `js/pages/distribute.js`：得分环改读 `r.quality.total`（无则用 `r.score`）；「改写调整清单」上方新增「平台质检」块：7 维条形 + 前 3 条 issue + 一句"代理指标，不代表平台流量"；发布弹窗文案由"适配度"改"质检分（代理指标）"；`publish({title, body})` 契约不变。
- `js/rewrite.js`：保留 `CP.genRewrite` 并标 `@deprecated`，仅作基线，不删以免破坏调用。
- `index.html`：在 `rewrite.js` 前按 analysis→strategies→planner→writer→quality→pipeline 顺序插入 6 个 script。
- `styles.css`：新增 `.quality-*`（质检分项条/issue 卡片），沿用既有设计变量与圆角风格。
- `package.json`：新增 `eval`、`eval:ai`、`eval:baseline`、`eval:calibrate` scripts（无新依赖）。

## 八、实施步骤（小步可验证）

1. **基线**：建 `eval/cases` + `eval/run.js`，跑旧引擎生成 `eval/baseline.json`。验证：`npm run eval -- --engine=old` 稳定出表。
2. **分析器**：`analysis.js`。验证：10 篇类型判定 ≥9 正确，数字/代码块/关键词可打印。
3. **策略+规划**：`strategies.js` + `planner.js`。验证：6 类型 × 4 平台计划稳定，`mustKeep` 非空。
4. **质检器**：`quality.js`。验证：旧引擎跑分明显偏低，issue 可解释、可定位。
5. **离线成稿**：`writer.js`。验证：无 Key 下 coverage ≥80、P0=0、长度合规 100%。
6. **流水线接入**：`pipeline.js` + `api.js` + `distribute.js` + `index.html` + `styles.css`。验证：改写、切 tab、复制、发布全链路不回归。
7. **AI 三段 + 修复**：验证 `npm run eval:ai` 3 次调用内完成、可降级、相对离线 +5。
8. **校准**：`eval/calibrate.js` + baseline 回归判定。

## 十、风险与边界

- **无 AI Key**：只做结构、取舍、排版、长度优化，不生成新论据，深度有限，UI 标明"本地引擎"。
- **LLM 不稳定**：白名单 + 数字子集 + 长度/禁忌校验 + 一次修复重试，坏结果不入库。
- **评测过拟合**：只比维度均值与阈值，不比固定句子；保留 holdout 用例并定期轮换。
- **爆款不可承诺**：统一使用"质检分 / 代理指标"，真实效果以平台回拉数据校准，样本不足不下结论。
